# x-scout

Local app: one Run button does a staged daily pass over X through a real Chrome profile (Playwright): News → Big accounts → Viral → Trash → Topics. Each stage is a few human-paced searches, a local candidate filter and one `claude -p` call with its own prompt (`x_scout/stages.py`); Claude reads a stage while the next one is scraped, so tabs fill up one by one (~30 min). Every card has a "done" box stored per run; the Checklist tab counts them and adds manual items and Claude's recommendations from the end-of-run summary. Topics (optional, last stage) are the older engine: up to 10 topics, early-virality scoring (ported from github.com/Sentimenta1ist/x-viral-radar `scoring.js`), one `claude -p` per topic picking posts to reply to and to read, each with a breakdown.

- Staged run (`pipeline.run_day`): one `browser.Session` for the whole run (one Chrome, one page, one shared rate `Budget`, `search_pause` seconds between searches). Stage queries, candidate filters, prompts, line parser and card assembly live in `stages.py`; News also opens Explore → News (`Session.explore`, `parse.explore_items`: trends + posts, any GraphQL op, X renames them) and falls back to search only. Stage state and picks go to `runs.stages` (json, `db.update_stage`), candidates are kept there as `cands` for Re-analyze (`reanalyze_day`), stripped from the API. Card checkboxes: `runs.checks` via `POST /api/runs/{id}/checks`, keys `<stage>:<post id>`, `m:<manual item>`, `rec:<i>`. A 429 / lost login keeps the stages already handed to Claude; Stop cancels everything. Trash replies have a daily limit in Settings (`trash_limit`); the prompts forbid connect / follow-for-follow replies. UI: `static/day.js` (stage tabs, cards, checklist), loaded before `app.js`. The reader profile (`data/profile.md`) carries the posting strategy and his opinions (used for OPPOSITE quote drafts).

- `x_scout/browser.py` Playwright, persistent profile in `data/browser-profile`. Reads X's own `SearchTimeline` GraphQL responses, never the DOM. Keep it human-paced (randomized pauses, few scrolls); read `x-rate-limit-remaining/-reset` and wait for the reset (up to 16 min) instead of running into a 429; a 429 that can't be waited out keeps what was read and the run is still analyzed. Per topic also a Latest `from:` search over known authors (`topic.authors` from Settings + `db.good_authors`: authors of past q>=4 picks, max 15). Order (`search_plan`): main searches of all topics, then authors, then extra queries, so a limit costs extras, not whole topics. Top uses `since_time` (exact 24h) + `min_faves:3`, falls back to `since:<date>` if X ignores it. No clicks, likes, follows, posting. Per topic, all over the last day: main query Top + Latest, plus one Top search per extra query (`topic.extra`, Claude writes 3 when the key is absent). Wider net, not a longer window: older posts repeat between daily runs.
- `x_scout/parse.py` GraphQL → flat post dict. X moves fields between schema versions; look up new place first, then legacy.
- `x_scout/scoring.py` pure scoring, tests in `tests/`.
- `x_scout/analyze.py` candidate pre-filter, compact pipe-delimited digest (with reach = views/followers and bm = bookmarks/like), `rank_topics` runs `claude -p` per topic with a short custom system prompt, `--tools ""`, `--setting-sources ""`, empty cwd; a failed topic falls back to local ranking. Output is a header line per pick (`R n q`) followed by field lines (`GIST`, `CONTEXT`, ...); the old one-line format still parses. Quality over tokens, but measure `usage` after prompt changes.
- `x_scout/pipeline.py` orchestration and live state; `app.py` HTTP API.
- Profile analysis (one X account, the Profiles section of the left sidebar; new features get their own sidebar item via `VIEWS` in `app.js`): `browser.scrape_profile` reads `UserByScreenName` + `UserOriginalsTimeline` / `UserRepliesTimeline` JSON (X renames these; see `POST_OPS`, `REPLY_OPS`) in the same Chrome session, `parse.py` (`profile_from_user`, `timeline_page`, `finalize_timeline`) flattens it, `profile_metrics.py` is pure local metrics (breakout = views >= 5x the median of the 30 previous original posts), `profile_analysis.py` is the one `claude -p` call (line format, always `profile_model`, default sonnet, independent of the search model), `profile_store.py` handles `data/profiles/<handle>/`, `static/profile.js` is the section. Shares `pipeline.state`, `_busy` and Stop with topic runs (`state.kind`). Stop / 429 / lost session keep the partial scrape without calling Claude. Re-analyze uses the stored scrape: use it for prompt tuning. Growth phases are inference from views, keep them labeled so.
- Post analysis (Post section): `post_analysis.parse_ref` takes a link or text, `browser.scrape_post` opens the post once and finds it in any `*Tweet*` GraphQL response (`parse.post_detail`, including Article bodies and the author's thread), one `claude -p`; `static/post.js`; records in `data/posts/`. Pasted text never opens X. DRAFT lines may use only the reader's own stories.
- Topic picks: `analyze.assemble` shows only q >= 4 and sends replies without reach (`has_reply_reach`) to Read; empty columns are expected, never fill them. During a run the UI stays on the run being viewed and opens the new one when it finishes.
- Sidebar sections are `VIEWS` in `app.js`: Today (staged run; the Topics stage is one of its tabs), Profiles, Post, Settings. Keep first screens short: details go in a folded section (user feedback: Profiles was overloaded, then the Topics board too). Topics is one quiet column (`pick()` in `app.js`): meta line, gist as headline, why, replies; context, spread, take, doubt, full text and numbers fold out. `card()` stays for Profiles and Post.
- `data/` (gitignored): sqlite db, browser profile, `settings.json`, `profile.md`, `profiles/`, `posts/`. Never commit it.
- Tests: `uv run pytest`. Run: `./run`. Demo data: `scripts/demo.py`; README images: `scripts/screenshots.py` against a demo server.
- Re-analyze (UI button / `POST /api/runs/{id}/reanalyze`) re-runs Claude on stored candidates without scraping: use it for prompt tuning.
